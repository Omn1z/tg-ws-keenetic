# Размер, память и скорость

Не сравнивайте размер Windows-сборки (системный Schannel) с Linux-релизом
(статический OpenSSL). Не переносите показатели ARM64 на MIPS без AES-инструкций.
Минимальный размер, максимальная скорость и минимальная RAM — разные параметры;
профили `release` и `speed` позволяют сравнить компромисс на нужном устройстве.

## Версия 2.1.0: шесть архитектур и обновление — 15 сентября 2026

Коммит `2e65051` прошёл [полную матрицу Actions](https://github.com/Omn1z/tg-ws-keenetic/actions/runs/34895883786).
Все шесть бинарников статические: без ELF-интерпретатора и зависимостей `NEEDED`.
Размеры включают TLS и встроенную панель; архивы также содержат установщик,
сервисы и лицензии. Значения округлены до сотых МиБ.

| Архитектура | Бинарник | Архив |
|---|---:|---:|
| MIPS | 4,77 МиБ | 2,11 МиБ |
| MIPSel | 4,77 МиБ | 2,10 МиБ |
| ARMv5 | 3,85 МиБ | 2,01 МиБ |
| ARMv7 | 3,85 МиБ | 2,00 МиБ |
| ARM64 | 5,34 МиБ | 2,73 МиБ |
| x86_64 | 6,32 МиБ | 2,48 МиБ |

Для MIPS и MIPSel подтверждены ABI o32, MIPS32r2 и soft-float; проверка запуска
выполнена в QEMU на 24Kc без FPU. ARMv5TE запущен на эмулируемом ARM926.
Это проверки совместимости, а не измерения производительности этих роутеров.
Нативная ARM64-сборка прошла 39 модульных и 4 интеграционных теста.

На том же Keenetic установлен ARM64-артефакт из этой сборки: ELF 5597072 байта,
архив 2861997 байт. SHA-256 архива совпал после передачи. Установка выполнена
через `update-worker.sh` с проверенным локальным пакетом CI; worker завершился
со статусом `complete`, удалил временный пакет и свою блокировку. SHA-256
конфигурации до и после совпал, сервис работает после закрытия SSH.

Панель автоматически проверила GitHub при открытии; ручная кнопка «Проверить»
также отработала. Установленная версия `2.1.0` не предлагает откат на текущий
публичный релиз `1.2.0`. Установка новой версии запускается только кнопкой
«Обновить». Блок команд установки, обновления и удаления из панели убран;
инструкции находятся в README и INSTALL.

Проверки Telegram для DC2 и DC4 получили корректные `resPQ` примерно за 422 мс
каждая. Во время серии были активны другие клиенты, поэтому маршрут каждого
запроса отдельно не установлен; суммарно счётчики выросли на четыре WS,
без TCP fallback и ошибок. После проверок версии, при двух активных клиентах:
RSS 7072 КиБ, пиковый RSS 7128 КиБ, один поток. Это не замер простоя или нагрузки.

Публичный релиз Rust на момент проверки не опубликован. Поэтому загрузка
более нового публичного релиза с последующей установкой кнопкой пока не
проверена на роутере целиком. Проверены получение метаданных GitHub, защита
от отката и применение пакета штатным worker; загрузка, ограничения размера,
проверка SHA-256 и восстановление после ошибок покрыты автоматическими тестами.

## Проверено на Keenetic ARM64 — 14 сентября 2026

Сборка из коммита `9afd06a`, Rust 1.97.0, профиль `release`, musl 1.2.4,
статический OpenSSL, встроенная панель. [Успешная сборка и тесты ARM64](https://github.com/Omn1z/tg-ws-keenetic/actions/runs/34892539566).
Устройство: два Cortex-A53 с AES/PMULL, ядро `4.9-ndm-5`, Entware;
`MemTotal` — 497676 КиБ. Параметры: буферы 16 КиБ, пул выключен,
лимит 64 подключения.

| Измерение | Результат |
|---|---|
| Статический ELF, с TLS и панелью | 5465936 байт — 5,21 МиБ |
| Архив с сервисами, установщиком и лицензиями | 2795605 байт — 2,67 МиБ |
| RSS после двух последовательных проверок, без активных клиентов | 6916 КиБ — 6,75 МиБ |
| Пиковый RSS этой первой серии (`VmHWM`) | 7012 КиБ — 6,85 МиБ |
| Потоки после завершения DNS | 1 |
| DC2, подключение + `req_pq_multi` → `resPQ` | 485 мс, прямой WebSocket |
| DC4, подключение + `req_pq_multi` → `resPQ` | 453 мс, прямой WebSocket |

Контрольная сумма архива после передачи по SSH совпала с локальной. Установка
выполнена штатным `install.sh --system entware --binary ...`; сервис запущен
через `/opt/etc/init.d/S99tgwsproxy`. Панель и API доступны на порту 1434,
прокси — на 1433. Проверка ELF в CI подтвердила отсутствие динамических
зависимостей. Конфигурация имеет права `0600`.

В первой изолированной серии оба ответа Telegram прошли проверку структуры и
nonce; прирост счётчиков — два WS, ноль CF/TCP fallback и ноль ошибок WS.
После перезапуска сервис снова вернул оба `resPQ`, а SHA-256 конфигурации
остался прежним. Затем панель показала активные клиентские подключения и
растущий WS-трафик. Автозапуск установлен; перезагрузка всего роутера не выполнялась.

Это проверка установки и сетевого протокола, не замер пропускной способности.
Скорость загрузки медиа, длительная нагрузка и потребление на бюджетных MIPS
этой проверкой не измерены. Указанный RSS относится к первой короткой серии,
а не к пределу памяти при 64 клиентах.

## Размер

После сборки Linux-матрицы скачайте архив своей архитектуры. Сравнивайте отдельно
размер `.tar.gz` для загрузки и распакованного ELF для flash:

```sh
wc -c tgwsproxy
file tgwsproxy
readelf -l tgwsproxy
readelf -d tgwsproxy
```

В статическом ELF не должно быть интерпретатора и `NEEDED`. Релизный workflow
проверяет это автоматически. UPX не используется: выигрыш flash за счёт упаковки
может увеличить память и время старта на слабом роутере.

## RAM на роутере

Найдите PID командой `pidof tgwsproxy`, затем:

```sh
PID=$(pidof tgwsproxy)
awk '/VmRSS|VmHWM|VmSize|Threads/ {print}' /proc/$PID/status
cat /proc/$PID/smaps_rollup 2>/dev/null
```

Снимайте замеры после минуты простоя, при 1/8/16 активных Telegram-соединениях,
при загрузке большого видео и после закрытия клиентов. `smaps_rollup` есть не
на всех ядрах. Память socket buffers ядра не входит в RSS процесса.
Учитывайте число потоков DNS, хранилище сертификатов и память TLS handshake.

По умолчанию: два пользовательских буфера по 16384 байта на соединение,
`max_connections=64`, `pool_size=0`. Дополнительно выделяются состояние AES/TLS,
задачи, ограниченные заголовки и Fake TLS record buffers. Это не обещание
«32 КиБ RSS на клиента». Большие сообщения передаются частями; размер сообщения
не определяет объём буферов прокси.

## Скорость

На одном роутере, с одинаковыми маршрутами DC, TLS, secret и числом клиентов:

1. Выполните три загрузки одного большого файла из Telegram через Python-версию;
   запишите среднюю скорость, загрузку CPU и пик RSS.
2. Повторите с Rust `release` при 4/16/64 КиБ и выключенном пуле.
3. Сравните `speed` с `release`; затем проверьте `pool_size=1` отдельно для времени
   подключения, поскольку прогретый пул в первую очередь сокращает TLS handshake.
4. Между сериями проверяйте, что трафик идёт тем же маршрутом (WS/CF/TCP), а не
   сравниваете разные fallback-серверы или состояние кеша клиента Telegram.

Зафиксируйте модель, CPU, endian, версию ядра, Rust/commit, профиль, размер ELF,
буферы, количество клиентов, RSS/peak RSS, CPU, Мбит/с и время подключения.
До этих измерений утверждать конкретное ускорение относительно Python нельзя.
